# Cross-border MVP

Текущий AI-пайплайн и Ozon-публикация: [SUBSCRIPTION-PIPELINE.md](SUBSCRIPTION-PIPELINE.md).

## Фактический статус

| Возможность | Реализовано | Ограничение |
|---|---|---|
| Ozon экономика и реклама | Реальные read-only Seller/Performance API | Неполные данные помечаются; начисления не равны прибыли |
| WB каталог, категории, отзывы/вопросы | HTTP read-only адаптеры | Без токена не проверены на кабинете; первая страница, не полный магазин |
| Taobao/Tmall импорт | Проверка URL и нормализация структурированного JSON | TOP API не подключён; сайт по ссылке не скачивается |
| Перевод и изображения | Codex по подписке: перевод/OCR, PNG с заменой текста; прежний fixture-DEMO сохранён | Один явно заданный однотонный текстовый регион; не универсальный inpainting |
| Маппинг | Реальный запрос дерева Ozon / списка WB; демонстрационный маппинг | Обязательные поля и значения Ozon проверяются API; WB и юридическая проверка требуют доработки |
| Публикация и цена Ozon | Точное подтверждение payload; адаптеры create и RUB-цены из эксперимента | Реальная отправка не испытана; цена требует свежих данных, отсутствия конфликтующих промо и текущего периода теста |
| Остатки, ответы, WB-записи | Подтверждения и mock-исполнение | Реальные записи отключены |
| Дайджест и алерты | По запросу: загруженные остатки, низкие оценки, блокеры | Нет планировщика, полного мониторинга возвратов, жалоб и модерации |
| Оценка выхода на рынок | Явная unit-экономика Ozon/WB, список недостающих данных | Нет исследования спроса/конкурентов; не заключение по одной ссылке |

## Архитектура

`core/canonical.mjs` — единая схема; `adapters/agents.mjs` — отдельные стадии с собственными инструментами; `core/workspace.mjs` — конечный автомат; `adapters/marketplaces.mjs` — адаптеры площадок. Есть детерминированный DEMO и отдельный режим реального Codex для текста/OCR. Публикация требует человека.

`import → extract → translate → image_edit → map_attributes → validate → review_gate → publish → sync`.

Перед вызовом инструмента сохраняются состояние running и tool.start. Результат применяется только для текущего runToken; повторный запуск отбрасывает устаревшие результаты. Каждый этап сохраняет вход, результат, prompt при наличии, хеши и время. Правка сохраняет исходник и версии перевода, повышает revision и отменяет последующие проверки и согласования. Повторный импорт идентичного товара дедуплицируется.

Три гейта: подтверждение перевода/категории; подтверждение точного публикационного плана; подтверждение русского ответа покупателю. Цена и остаток также проходят очередь. MVP требует проверки каждой карточки; автоодобрение следующих карточек категории пока не включено.

При исполнении операция сначала персистентно становится executing. Успешный повтор возвращает прежнюю квитанцию. Неоднозначный сбой становится unknown и не повторяется автоматически. Создание карточки Ozon имеет payload, ограничение частоты и polling статуса импорта. Для других записей ещё нужны адаптеры, идентификаторы складов и reconciliation внешних операций.

Данные: `runtime/workspace.json`, атомарная запись, файл 0600, каталог 0700, очередь мутаций. Audit — цепочка SHA-256: обнаруживает изменение записи, но не заменяет внешнее неизменяемое хранилище. Один локальный процесс; не проверено для 5000 SKU или нескольких серверов.

## Подключение

Ключи не вводятся в браузер, не возвращаются API и не коммитятся. Существующие Ozon-пути читаются из `~/.config/ozon-ops-crew/connection.json` (см. LIVE-API.md). Дополнительные профили в том же JSON:

```json
{
  "stores": [
    {"id":"wb-live","name":"我的 WB 店铺","marketplace":"wb","mode":"live","envFile":"/absolute/private/wb.env"}
  ]
}
```

`wb.env`: `WB_API_TOKEN=...`. Для дополнительного Ozon: `OZON_CLIENT_ID` и `OZON_API_KEY` в собственном `envFile`. Для дополнительных магазинов ключи из переменных процесса не подставляются: неполный профиль должен завершаться ошибкой, а не читать другой аккаунт. Существующие поля connection.json сохранить. После изменения конфигурации перезапустить сервер. Создание Ozon и RUB-цена из сохранённого эксперимента доступны только через гейты. Перед ценой читаются свежие условия товара; неподходящие промо, валюта, затраты и просроченные подтверждения блокируют запись. Остатки, ответы и WB-записи не включаются настройкой `writesEnabled`.

Не размещать этот сервер в открытом интернете: он слушает localhost, многопользовательской авторизации пока нет. Маскирование email/телефонов в сообщениях эвристическое; это не доказательство соответствия GDPR/152-ФЗ. Перед production нужны полноценные PII-политики, удаление/retention, разграничение доступа и внешнее хранение секретов.

## Демо 5–7 минут

1. Главная: реальный Ozon отдельно от двух DEMO-магазинов; перейти в 商品迁移.
2. Нажать 运行示例商品: фиксированный синтетический товар, без заявления о загрузке Taobao.
3. 运行至人工确认: увидеть стадии, исходник ZH, RU-черновик и две пары шаблонных картинок.
4. Изменить русский заголовок, сохранить и повторно выполнить проверки. Подтвердить перевод/категорию.
5. Создать публикационный план, проверить русское содержимое, подтвердить версию и исполнить симуляцию. Никакой реальной карточки не создаётся.
6. На главной у DEMO-магазина создать демонстрационный отзыв. В 客户沟通 проверить ZH-перевод и RU-ответ; подтвердить и исполнить в очереди.
7. 市场评估: вставить Taobao-ссылку. Без расходов получить «недостаточно данных», затем заполнить экономику обеих площадок и сравнить условную прибыль.

## Метрики и следующие обязательные шаги

Реальных SKU в бенчмарке: 0. ≤10 минут, ≥80% полей без правки и ручной baseline 2–4 часа — цели/гипотезы из ТЗ, не результаты. Один синтетический AI-прогон занял около 95 секунд без публикации; скорость fixture не считается измерением AI. Стоимость LLM/OCR, модерация с первого раза и качество локализации ещё не измерены.

Для полного сценария нужны TOP-доступ или реальные экспорты, реальные товарные характеристики, публичное хранение изображений и испытание write-адаптера Ozon; WB write-адаптер ещё предстоит реализовать. Затем замер на 10 реальных SKU с учётом ожидания модерации. Официальные API и доступность функций зависят от кабинета/прав; нельзя автоматически считать китайский и российский кабинеты эквивалентными.

Ссылки для сверки интеграций: [Ozon Seller API](https://docs.ozon.ru/api/seller/), [WB Content API](https://dev.wildberries.ru/en/openapi/work-with-products), [WB sandbox](https://dev.wildberries.ru/en/sandbox). Ограничения тестового стенда и реального кабинета проверяются отдельно.

## 商品利润实验

В китайском кабинете добавлен журнал ручных сравнений цены/рекламы по магазину и SKU. Два непересекающихся периода, полные затраты и реклама отдельно; результат нормализован по дням. Незавершённые расчёты, малая выборка или неподтверждённая сопоставимость не позволяют сделать вывод. Записи сохраняются с audit hash; никаких действий на площадке не запускают. Это наблюдения, а не доказанный причинный эффект. Направление продукта и оставшиеся шаги: [PRODUCT-FOCUS.md](PRODUCT-FOCUS.md).

## WB: обязательные характеристики

Добавлен read-only адаптер `/content/v2/object/charcs/{subjectId}?locale=zh` и просмотр обязательных полей на главной для настроенного live WB-магазина. `required` берётся из ответа, а не выводится из `hasFilter`/популярности. Проверяются ID категории/характеристик, схема и дубликаты; обращения этого адаптера сериализованы с интервалом 650 мс. Это не общий лимитер всех WB API.

Основание: [официальная документация WB](https://dev.wildberries.ru/en/openapi/work-with-products), [изменение обязательных характеристик](https://dev.wildberries.ru/release-notes?id=272). Контракт проверен контролируемыми ответами; WB токеном на текущем аккаунте ещё не проверен. Маппинг значений и публикация WB остаются незавершёнными. Для WB-товара больше не показывается форма публикации Ozon.
