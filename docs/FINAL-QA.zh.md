# 决赛问答准备 / Final Q&A preparation

线下决赛（10 月 24–25 日）可能被问到的问题与建议回答。所有回答必须与仓库证据一致，不夸大已实现能力。

## 技术方案（25%）

**问：这是真正的多智能体系统吗？**
答：当前是六个职责明确的智能体阶段（数据管理→单元经济→库存需求→策略→风控→执行审计），以确定性规则实现，每 30 秒显式运行完整任务流程并记录阶段序列与回执。LLM 规划用于决策解释与需求叙述，不直接改写价格与预算——所有写动作由确定性规则和商家限额把关。架构契约见 ARCHITECTURE.md 智能体表。

**问：为什么用规则而不是直接让大模型决策？**
答：价格与预算是资金写操作，需要可复现、可审计、可测试。规则引擎有 36 项自动化测试与幂等性保证；LLM 输出不可复现，只适合解释层。这是有意的人机协作设计，不是能力缺失。

**问：数据从哪来？**
答：Ozon Seller API 只读目录（已在卖家本机验证）；采购与销售窗口由 Excel 导出的 CSV 导入并经 schema 校验；结算数据在试点阶段接入（见 EVALUATION.md 试点计划）。

## 业务价值（25%）

**问：效益数字的依据是什么？**
答：两层。第一层是可复现模型：`node scripts/value-model.mjs` 用真实引擎跑固定种子的 10,000 SKU 组合，聚合引擎决策处理的敞口（每卖家/月约 68 万卢布止损保护、约 4.4 万卢布仓储敞口、约 37.6 小时人力节省）——假设全部写在 VALUE-MODEL.md。第二层是试点计划：影子模式→对照组→公布样本量与区间。我们明确不宣称已实现实盘收益。

**问：卖家为什么不用 Ozon 后台自带工具？**
答：平台后台分别管理广告与价格，不把库存天数、补货周期、仓储成本与汇率放进同一个利润决策；也没有滚动亏损（含未分摊广告费）的自动熔断。我们的差异化是「利润×广告×库存」一体化。

## Demo（20%）

**问：Demo 能跑多少数据？**
答：现场可在「数据与补货」页一键生成 500 SKU 压测组合，决策与页面交互保持流畅；引擎实测约 35 万 SKU/秒/核，全组合 10,000 SKU 一轮约 28 ms。瓶颈不在计算，在平台 API 配额与数据摄取——SCALING.md 有针对性架构。

**问：公开演示会不会泄露真实数据？**
答：不会。公开演示只含合成数据；真实目录读取只在卖家本机、密钥存于外部文件、仓库零密钥（COMPLIANCE.md）。

## 创新与扩展（10%）

**问：能复制到其他平台吗？**
答：决策逻辑与平台解耦；接入 Wildberries、Yandex Market、速卖通、Temu 只需实现各自的摄取与执行适配器，引擎与审计账本复用。每个平台独立验证费率与权限后才开放写入。

## 安全与合规（5%）

**问：会不会误停共享广告活动里其他商品？**
答：执行状态机在暂停前校验 SKU 与活动的成员关系，超时按未知处理并人工复核；当前原型只做本地模拟执行，真实写入默认关闭。

**问：数据合规？**
答：原型数据只存操作者浏览器；生产设计为行级租户隔离 + 按卖家 KMS 加密密钥；遵循 PIPL 与俄罗斯 152-FZ 的最小化原则。
